### 1.7 Submission and observation surfaces

The plan's §4 names this as part of T00's deliverable — "the actual tooling
available to submit and observe governed work" — and its §7 step 2 warns not to
bypass a terminal or ancestry restriction. Established here rather than assumed.

**Submit:**

```text
sensei-code submit --task "..."        places one objective into the running control process
sensei-code run --task "..."           headless governed run; exit 0 complete · 1 failed
                                       · 3 awaiting human authority · 4 stopped · 5 timed out
sensei-code observe --task "..."       read-only lane; exit 6 observed, repository unchanged
sensei-code audit-repair --task "..."  observes, then opens a separate governed task per finding
sensei-code proposal list|show|approve inert GitHub-received objective proposals; approve
                                       selects the exact stored bytes
```

Transport is the loopback control surface on `127.0.0.1:10123` plus the unix
socket `.sensei-code/control.sock`, with `.sensei-code/control-token` (mode
`0600`) beside it. There is no `--from-json` and no importer; the plan's warning
against inventing one is correct — none exists.

**The origination restriction is real and mechanical.**
`internal/control/local.go:559` `mayOriginateObjective` refuses on three
independent grounds, each with its own message:

```go
if p.UID != selfUID          { ... }   // the channel belongs to another uid
if p.Descendant              { ... }   // a worker this orchestrator launched may not
                                       // originate work: implementing one objective
                                       // does not confer authority to create another
if p.Terminal == 0           { ... }   // no controlling terminal; an objective is
                                       // placed by an operator at one
```

The peer facts come from the kernel at connect time
(`internal/control/peer_linux.go:20-33`), and the judgement is deliberately split
from the observation so a test cannot stub the decision.

**Consequence for this and any assistant-run session.** `tty` in this session
returns `not a tty` (pid 336141, `TT` = `?`). An assistant working through a
non-interactive shell therefore **cannot** submit a governed objective, by
design and by kernel-observed fact, not by policy text. Per plan §7 step 2 the
correct handling is to hand the owner the exact objective bytes to submit at a
terminal. Allocating a pty to satisfy the check would be defeating the control,
not satisfying it.

**Observe:** `sensei-code proposal list|show`, the control surface's typed task
views (`internal/control/inspect.go`, which distinguishes `Absent` — no record
exists — from `EmptyProven` — the record exists and holds no such fact), the
event stream via `run --json`, and the durable per-task records under
`.sensei-code/tasks/*.json` in the `taskstate` v2 shape.

## 3. Findings

### F1 — the readiness check queries an address the repository does not use, and prescribes a repair that would repeat a known custody fault

`internal/setup/checks.go:213` and `:239`:

```go
out := run(ctx, o.RepoRoot, "sensei", "metadata")     // no -addr
...
c.Detail = "answering on " + fallback(o.GraphAddr, "localhost:10120")
```

`Options.GraphAddr` is populated from configuration (`internal/setup/inspect.go:26,111`)
and is referenced at exactly one place in the whole package: the success
*message*. It never reaches the command. So the check queries `:10120`, which
nothing serves here, and reports the repository's healthy `:10122` server as
`BROKEN`. Reproduced live in §2.3 against a server that answers correctly in §1.4.

Two consequences, and the second is worse than the first:

* The printed remedy is `sensei serve -no-seed &`, which would start a second
  server on the default port over a different store. `docs/open-items.md` records
  that same custody mistake three times, and `checkGraphFreshness`'s own comment
  explains how a cross-repository rebuild breaks every other repository sharing
  a store.
* In the passing direction the check is worse still. If `:10120` *did* answer —
  as it would on a machine that also serves another project — the check would
  report `OK` and print `"answering on " + o.GraphAddr`, naming the configured
  address while a different graph answered. That is a false green, not a missing
  check.

`graph freshness` inherits the same defect, which is why §2.3 reports
`freshness not reported`.

This is the recurring "a name is not a scope" shape: a check that accepts a
scope, states it in its output, and does not use it in its body.

### F2 — the MCP binding for one configured agent points at the other repository's graph

`doctor` FAIL and `setup` warn, both live: `mcp:codex` points at `localhost:10121`
(the `github.com/globulario/sensei` domain) while this repository is configured
for `localhost:10122`. `codex` is a configured provider on this machine: `config.Default()`
makes it both a default implementor and the default reviewer, and `doctor`
reports it authenticated. (This repository's `.sensei-code/config.json`
overrides the reviewer roster to `chatgpt` with `graph: none`.) Either role
consulting another repository's architectural graph is a correctness problem,
not a convenience one — an implementor would plan against the wrong invariants,
and a reviewer would judge against them.

The repository detects it and offers a one-command repair
(`sensei-code mcp codex`, or `setup --apply`). It is unrepaired at this revision.
Applying it is a mutation and outside T00.

### F3 — the `sensei` CLI default address is served by nothing

`ss -ltnp` shows no listener on `:10120`. Every `sensei` invocation without

will bite any operator following documented commands
(`AGENTS.md` and `CLAUDE.md` both print `sensei briefing --file <path>` with no
address, and `AGENTS.md` states the default is `localhost:10120`).

### F4 — the facts a campaign needs before spending a request are in no readiness surface

`doctor` and `setup` between them cover: executables, provider authentication,
the Sensei MCP tool surface, per-agent MCP binding, graph server reachability,
graph freshness, domain registration, corpus presence, worktrees, and task
binding staleness. `grep` finds **no** reference to `doorbell`, to
`internal/roles`, or to provider quota in `internal/doctor`, `internal/setup` or
`internal/report`.

So, concretely, at this revision the running control process has
`-github-bridge-roles none`, and no readiness command says so. The exact things
T05 enumerates — architect role assigned, doorbell enabled, credential
capability, deadline coherence, provider quota — are the things not covered. The
provider rows are already honest about their limit (`UNPROVEN … does not spend
provider quota`), which is the right pattern for the missing ones to copy.

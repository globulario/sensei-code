### What the gap actually was

Narrower than §1 assumed, and worth correcting here. `TerminalAbandoned` AND
`PhaseAbandoned` both already existed. What was missing was the **event type**
to carry them: `LedgerEventTypes` had `completed` and `revoked` and no
`abandoned`. So the vocabulary could describe the state in two of three places
and no event could write it.

A second structural fact decided the shape:
`ValidateCompletionReceipt` **requires** a non-empty `ResultBinding` and a
`CertificationDigestSHA256`. An abandoned task has neither. Reusing
`CompletionReceipt` would have forced one of two lies — a fabricated result
binding, or a validator relaxed for every caller including real completions. So
`AbandonmentReceipt` is a separate shape **with no result field at all**, and
its validator refuses any status but `abandoned`, an empty reason, and
`no_result_produced != true`.

### Files

| File | What |
|---|---|
| `closureprotocol/vocabulary.go` | `LedgerEventAbandoned`, added to the closed list |
| `closureprotocol/model.go` | `AbandonmentReceipt` — no `ResultBinding` field exists |
| `closureprotocol/validate.go` | `ValidateAbandonmentReceipt` |
| `tasksession/session.go` | `ClearActivePointer(repoRoot, expectedTaskID)` — in the pointer's only writer |
| `completion/abandon.go` | `AbandonTask`, reusing lock, ledger, identity and `resolveCompletionAuthority` |
| `cmd/awg/cmd_abandon_task.go` + `main.go` | `sensei abandon-task`, beside `complete-task` |

No parallel authority store: the lock (`governedmutation.AcquireLock`), policy
index, identity manifest, actor verification and authority resolution are the
same owners `CompleteTask` uses.

## COMMISSIONING BOUNDARY 2026-09-09 — merging the code does not commission the operation

Owner ruling, recorded here because it governs §6 of this binding and is easy to
get wrong in exactly one direction.

Round three of the #350 review made abandonment its own governed operation:
`authority.sensei_terminal_abandonment`, `grant.sensei.terminal_abandonment`,
`mutation_path.terminal_abandonment`. Those live in `authority_domains.yaml`,
`authority_grants.yaml` and `mutation_paths.yaml` — which are **graph sources**,
not merely repository files. The published `awareness.nt` changed accordingly,
and the three new subjects are visible in the generated diff.

**So the merged binary resolves authority against whatever the live graph holds,
which after a merge is still the OLD corpus.** Abandonment would be refused —
`grant_cover_missing:authority.sensei_terminal_abandonment` — not because the
repair is wrong but because the authority it needs has not been published.

### The required order after an exact-head acceptance and merge

```text
1. verify the merge commit directly
2. rebuild/publish the graph from admitted main, explicitly scoped store
3. confirm the new domain, grant and mutation path are retrievable and authoritative
4. exercise positive AND negative authorization probes
5. only then run the merged command against task.defect.b3852005b2c6
```

Step 4 is not optional decoration. A positive probe alone cannot distinguish "the
new grant is published and working" from "something else authorized it" — which
is the precise defect round three repaired. The negative probe is what makes the
positive one mean something.

### Why the tempting shortcut is wrong

Running F5's abandonment immediately after the merge would **test an old graph
rather than the new operation**. If it refused, the refusal would be read as a
defect in the repair. If it somehow succeeded, that success would be evidence
that abandonment is still borrowing authority it is not supposed to have. Neither
outcome measures what it appears to measure.

This is the session's recurring shape at the deployment layer: *the mechanism
exists in the tree, and the tree is not what governs the running system.* The
same distinction produced B4 (a binary serving a corpus revision nobody
published) and the round-one/two/three findings generally.

**§6 of this binding is amended accordingly**: the application step is gated on
steps 1–4 above, not merely on "reviewed and merged".
